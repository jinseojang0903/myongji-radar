# 매일 공지 수집과 규칙 분석 운영

이슈 #31, 작성일 2026-11-04.

## 결정과 완료 상태

- **위치:** 김경민의 개인 Windows PC. 전용 운영 저장소의 `pipeline/data/`에만 원문·DB·로그를 보관하고 Git에 올리지 않는다.
- **시각:** 매일 한국시간 21:00. 당일 근무시간의 공지를 밤에 반영하고 오전에 PC가 꺼져 있을 가능성을 줄인다. 등록기는 `Korea Standard Time`을 확인한다.
- **단위와 확인:** 수집→규칙 분석을 한 작업으로 실행하고 날짜별 로그와 최신 상태 JSON으로 실패를 확인한다. 외부 메일·메시지는 발송하지 않는다.

구현·오프라인 시험·예약 정의의 WhatIf 검증을 완료했다. **실제 예약 등록과 서로 다른 실제 날짜 이틀 이상의 자동 성공 기록은 아직 없다.** 가짜 시계의 이틀 데이터 보존 테스트는 운영 실적이 아니다. 실제 운영 기준 충족 전에는 #31을 닫지 않는다.

#6의 11개 출처 등록과 main의 매일 공개(publisher) 구현을 반영했다. 이 실행기는 현재 수집→규칙 분석까지 실행하며 publisher 자동 호출은 아직 연결하지 않았다. 추출 PC로 DB를 자동 전송하지 않는다.

## 운영 조건

전용 운영 저장소는 `%USERPROFILE%\myongji-radar`처럼 **해당 Windows 사용자의 개인 폴더 아래**에 두고 main 브랜치를 유지한다. 다른 일반 사용자가 코드·설정을 바꿀 수 있는 공유 폴더나 공용 PC를 운영 위치로 사용하지 않는다. 개발과 브랜치 변경은 다른 작업 폴더에서 한다. 등록기와 실행기는 개발 브랜치의 실제 운영을 거부하며 `-WhatIf`·`-ValidateOnly`만 허용한다.

PC 전원과 **등록한 Windows 사용자의 로그인 상태**가 필요하다. 화면 잠금과 로그아웃은 다르며 로그아웃 상태의 실행은 보장하지 않는다. 현재 사용자·최소 권한(Interactive·Limited)으로 비밀번호나 관리자 권한을 저장하지 않는다.

StartWhenAvailable로 놓친 예약의 보충 실행을 허용하지만 즉시 실행이나 누락된 날짜별 재생을 보장하지 않는다. IgnoreNew와 데이터 폴더의 OS 파일 잠금으로 중복 실행을 막는다. 작업 스케줄러는 전체 실행을 1시간으로 제한한다. 강제 종료 뒤 상태가 collecting으로 남을 수 있으므로 작업 결과와 로그를 함께 확인한다. 개별 HTTP 제한 보완은 #11 범위다. [Microsoft 작업 설정](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/new-scheduledtasksettingsset), [놓친 작업 실행 설명](https://learn.microsoft.com/en-us/windows/win32/api/taskschd/nf-taskschd-itasksettings-get_startwhenavailable)

## 설치·사전 확인·등록·해제

Python 3.11 이상과 Git이 설치된 Windows에서 저장소 루트 기준으로 실행한다. PowerShell 파일은 Windows PowerShell 5.1의 한글 해석을 위해 UTF-8 BOM으로 보관한다.

```powershell
git switch main
git pull --ff-only
python -m venv pipeline/.venv
.\pipeline\.venv\Scripts\python.exe -m pip install -r pipeline/requirements.lock.txt
# 설정만 확인: 네트워크·DB·일일 상태 변경 없음
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_daily_collect.ps1 -ValidateOnly
# 작업 정의만 확인: 실제 등록 없음
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\register_daily_collect.ps1 -WhatIf
# PR 병합 후 전용 main 저장소에서 실제 등록
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\register_daily_collect.ps1
# 해제: 데이터는 유지
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\register_daily_collect.ps1 -Remove
```

기본 작업 이름은 `MyongjiRadar-DailyCollect-윈도우사용자명`이다. 시각 변경은 `-At '21:00'`, 다른 작업 이름은 `-TaskName`을 지정한다. 같은 이름의 작업이 있어도 실행 파일·인자·사용자가 일치하는 이 설치의 작업만 갱신·해제한다. 사용자는 계정 이름 문자열을 그대로 비교하지 않고 Windows 계정 조회로 SID를 확인한다. 따라서 `도메인\사용자`, 짧은 사용자명, SID 표현이 같거나 다르게 반환돼도 같은 사용자임을 확인할 수 있다. SID를 해석할 수 없거나 다른 사용자이면 거부한다. 다른 작업이면 중단한다. 실행 창은 숨김 처리한다.

저장소를 옮기려면 기존 경로에서 먼저 해제하고, 새 경로에 가상환경을 다시 만든 뒤 등록한다. 이미 옮겨 인자가 달라졌다면 다른 작업으로 간주하므로 작업 스케줄러 화면에서 기존 작업을 확인해야 한다.

## 수동 실행과 하루 한 번 정책

수동 일일 실행도 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_daily_collect.ps1`을 사용한다.

한국시간 날짜별 수집 **시도 1회**를 허용한다. 성공·수집 시작 후 실패·부분 실패 모두 당일 자동 재시도하지 않는다. 네트워크 전에 daily_status.json을 원자적으로 저장하므로 중단 후에도 같은 날 다시 요청하지 않는다. 출처·규칙 사전 검사가 네트워크 전에 실패하면 수정 후 다시 실행할 수 있다.

날짜 상태가 손상됐거나 미래 날짜면 요청하지 않고 실패한다. 파일을 임의 삭제해 우회하지 말고 PC 시각·백업·최근 로그를 확인한다. 강제 재시도 옵션은 없다. 일일 실행과 직접 CLI의 수집·내보내기·분석은 같은 데이터 폴더 잠금을 사용한다. 프로세스 종료 시 OS가 잠금을 해제하며 collector.lock 파일은 삭제하지 않는다.

### 날짜 상태 손상 복구

1. 현재 시각·시간대와 `data/logs/`의 `invalid_daily_state` 기록을 확인한다. 작업 스케줄러의 해당 일일 작업을 일시 중지한다. 수집·분석 프로세스가 아직 실행 중인지 확인하고 `data/` 전체를 비공개 위치에 백업한다. 잠금 파일 자체를 삭제하지 않는다.
2. `pipeline/`에서 다음 명령으로 **명시적 복구**를 실행한다. 사용자 지정 데이터 폴더를 썼다면 동일한 `--data-dir`을 붙인다.

   ```powershell
   .\.venv\Scripts\python.exe -m collector.daily --recover-state
   ```

3. 복구는 공통 잠금을 얻은 뒤 손상 원본 바이트를 `data/state_backups/*.bin`에 보존하고 정상 JSON 마커로 교체한다. 현재 날짜를 이미 시도한 것으로 보수적으로 표시하므로 **복구 당일에는 재수집하지 않고 다음 한국시간 날짜부터 재개**한다. DB·원문·분석 결과를 초기화하지 않으며 복구 과정에 네트워크 요청은 없다.
4. `daily_status.json`의 `manual_state_recovery_skip_today`와 백업 경로, 로그의 `state_recovered`를 확인하고 일일 작업을 다시 활성화한다. 다음 날 정상 실행과 이전 데이터 보존을 확인한다. 동작 시험은 가짜 시계 테스트로 하고 실제 PC 날짜를 바꾸지 않는다.

정상 상태에서는 아무것도 변경하지 않고, 상태 파일이 아예 없으면 복구를 거부한다. 백업 실패 시에도 손상 원본을 덮어쓰지 않는다. 종료 코드 0은 복구 성공 또는 이미 정상, 1은 상태 없음·파일 작업 실패, 2는 다른 작업이 실행 중임을 뜻한다. 실패하면 상태와 백업을 확인하고 원인을 해결한 뒤 다시 실행한다. 복구 뒤에도 종료 상태는 운영 성공으로 표시하지 않는다. 이 명령은 정상 마커를 삭제해 같은 날 재시도하게 만드는 우회 명령이 아니다.

기존 직접 `collector run`과 BAT 1·2번은 **날짜 게이트를 적용하지 않는 개발 시험 경로**다. 운영 중 추가 실행하지 않는다. 네트워크 없는 재분석은 BAT 6번 또는 collector analyze로 수행한다. 직접 CLI의 잠금 충돌은 종료 코드 2, 일일 실행기의 중복·당일 재실행 건너뜀은 코드 0이다. 건너뜀은 최근 시도 상태를 덮어쓰지 않는다.

## 로그와 실패 처리

| 위치 | 내용 |
| --- | --- |
| data/logs/YYYY-MM-DD.jsonl | 한국시간 시작 날짜별 시작·수집·분석·종료 또는 건너뜀 |
| data/daily_status.json | 최근 시도 시작·종료, 상태, 이번 수집 run_id, 출처별 신규·변경·변경 없음·오류 건수 |
| data/collector.sqlite3의 runs | 출처별 상세 오류 URL·이유 |

모두 pipeline 아래 data 폴더에 있다. 운영 JSONL에는 원문·제목·외부 오류 문자열을 복제하지 않는다. 예외 종류·실패 단계(failure_phase)·run_id·진단 위치를 기록한다. 수집 오류는 같은 run_id의 DB runs에서 상세 URL과 이유를 확인하고, 분석 오류는 네트워크 없는 collector analyze를 직접 실행해 확인한다. 설정 오류는 ValidateOnly로 확인한다. 날짜 상태 오류에는 복구 명령 안내도 기록한다.

일부 실패가 있어도 이번 수집이 정상 반환·내보내기를 마치고 한 건 이상 저장했으면 분석하며 최종 partial_failure·코드 1이다. 전체 실패·새 run 없음·미완료 run·내보내기 예외면 분석하지 않고 이전 분석을 유지한다. 자신의 run_id를 확인하므로 예전 실행을 이번 성공으로 오인하지 않는다. 분석 실패도 코드 1이며 수집 DB·원문은 보존한다. argparse의 SystemExit도 종료 코드로 처리한다.

첨부의 주소 정책·용량/개수/실행 예산 상한·HTTP 4xx(408/425/429 제외)는 `skipped` 경고다. 경고만 있으면 수집과 분석을 정상 완료할 수 있지만 모든 첨부를 확인했다는 의미는 아니다. 첨부의 타임아웃·429·서버 오류·로컬 저장 실패는 실제 수집 오류로 남는다. DB runs에는 `warnings`/`errors` 상세를, 일일 상태와 JSONL에는 각각의 건수를 기록한다. 다운로드 성공 후 변환만 실패하면 파일을 보존하고 원문 확인 필요로 남긴다.

### publisher 연결 계약 (#19)

main의 `python -m publisher --model <모델>`은 구현돼 있지만 이 일일 실행기에는 아직 연결하지 않았다. PR #44 병합 후 연결 작업을 정한다. 연결 시에는 수집과 규칙 분석이 **모두 성공한 뒤, 같은 CollectorLock을 유지한 상태**에서 publisher를 호출해야 한다. 잠금을 풀고 다시 획득하면 확인과 사용 사이에 다른 수집이 원문을 바꿀 수 있다. 수집 일부 실패에서 분석만 성공한 경우에도 자동 공개 단계로 넘어가지 않는다.

publisher의 종료 코드 0(새 카드 출력)과 1(출력했지만 내보내기 경고)은 정상 완료로 취급하고 경고 로그를 확인한다. 2는 중단이며 기존 cards.json을 유지한다. claude -p를 실행하는 본인 계정의 로그인이 있는 PC에서 동작해야 한다. 계정·토큰을 저장소나 스케줄러에 복사하지 않는다.

상태는 success / partial_failure / failed이며 강제 종료 중에는 collecting이 남을 수 있다. 상태 확인은 저장소 루트에서 다음처럼 한다. 날짜는 실제 확인할 날짜로 바꾼다.

```powershell
Get-Content .\pipeline\data\daily_status.json -Encoding UTF8
Get-Content .\pipeline\data\logs\2026-11-04.jsonl -Encoding UTF8
Get-ScheduledTaskInfo -TaskName "MyongjiRadar-DailyCollect-$env:USERNAME"
```

예약이 아예 시작되지 않으면 프로그램 로그도 없으므로 LastRunTime·LastTaskResult와 최근 로그 날짜를 함께 확인한다. 외부 watchdog·메일·웹훅은 아직 없다.

## 검증과 이틀 운영 확인

pipeline에서 `.\.venv\Scripts\python.exe -m unittest discover -s tests -v`로 실행한다. 가짜 응답·임시 DB로 두 날짜의 데이터 보존, 당일 중복 차단, 다른 프로세스 잠금, 부분·전체 실패, SystemExit, 손상 상태 차단, 원문 없는 로그를 시험했다. Windows에서는 실제 등록 함수를 막은 WhatIf로 작업 정의와 관계없는 작업 해제 거부를 확인한다. Windows 전용 테스트는 지원하지 않는 환경에서 건너뛴다.

PR 병합 후 실제 등록하고, 서로 다른 실제 날짜 이틀 이상 사용자 로그인 상태로 자동 실행한다. 두 날짜의 started→collection_finished→analysis_finished→finished(success), run_id, 이전 날 글 보존을 확인한 뒤 날짜·건수·종료 코드만 #31에 기록한다. 실제 원문·DB·로그 전체를 공개하지 않는다. 이 검증 전에는 #31 완료로 표시하지 않는다.
