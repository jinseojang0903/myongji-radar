옛 첨부 오류는 FetchPolicyError 152·ResponseTooLarge 1, 이미지는 FetchPolicyError 261로 저장되어 있다. 옛 FetchPolicyError는 주소 정책과 예산을 구분하지 않아 19개가 모두 실제로 복구될 것이라고 단정할 수 없다. 주소 검사는 네트워크 요청 없이 수행했다.

## 운영 판단

오늘 실제 재추출 대기로 빠진 카드는 0장이므로 기존 결과를 새 원문 판에 재사용하거나 호출 상한을 즉시 올리지는 않는다. 원문 변경 시 옛 값·근거가 남지 않게 하는 안전 정책은 유지한다. 다만 해시가 처음 붙으면 새 판이 되는 계약상 잠재 위험은 남아 있으며, 19개가 동시에 새 판으로 바뀌는 최악의 경우에는 max_new=5로 약 4회가 필요하다(다른 새 공지·실패·이미지 설정 등의 영향은 별도).

배포 후 첫 수집·공개의 `waiting_new_version`과 새 첨부 지문 생성 건수를 함께 확인한다. 실제 대기가 발생하면 기본안을 **일회성 따라잡기 실행의 max_new=20**으로 정한다. 기존 하루 호출 상한 60 안에서 여유를 확인하고, 당일 이미 실행된 이력·로그와 계정 상태를 확인한 운영자가 실행한다. 기본 max_new=5는 유지하며 주기 설정을 계속 높여 두지 않는다. 이 PR에서 실제 추가 AI 호출은 하지 않았다. 임의로 직전 버전 카드의 안전 제한을 해제하지 않는다.

## 코드 수정과 회귀

- 공지 단위 상한을 미수집 우선 처리 대상에서 제외해 다른 복구 가능 첨부가 순서를 차지하게 한다. 성공 파일의 매일 변경 확인 자체를 없애지는 않는다.
- 실패 기록에도 `same_attachment_input`을 사용한다. 첨부 링크는 있어도 실제 입력이 없던 옛 3회 실패 기록은 포기 상태를 유지한다. 새로운 첨부 입력이 생기면 기존처럼 횟수를 초기화한다.
- HTTP 영구 오류·다운로드 오류·실행 시간 만료의 사유, 실패 시 이전 파일 바이트·해시 보존, 옛 실패 기록 이관과 재호출 방지를 시험한다.

오늘 카드 수 변화가 첨부 복구 때문이라는 결론은 내리지 않는다. 실제 waiting_new_version은 0이며 과거 게시일 필터 등 별도 원인을 구분해야 한다.
