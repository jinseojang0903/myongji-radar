# 매일 수집과 카드 공개 연결 (#63)

## 실행 경로

`scripts/run_daily_collect.ps1` → `collector.daily --publish-config config/publishing.toml` → 수집 → 규칙 분석 → publisher(추출·검증·내보내기·카드 한 파일 main 푸시) 순서다. CollectorLock은 전체 구간에 유지한다. publisher 자체는 별도 잠금을 잡지 않으며 일일 실행기가 잠금을 보유한 상태로 호출한다.

기존 예약 작업은 같은 스크립트를 호출하므로 병합 후 최신 main을 운영 PC에 받으면 새 흐름을 사용한다. 기본 설정은 `enabled=false`이므로 운영자가 켜기 전에는 수집·규칙 분석까지만 수행한다. 이 PR 작업에서 작업 스케줄러를 새로 등록/변경하거나 실제 운영 수집·AI 호출·공개를 실행하지 않는다.

## 중앙 설정

`pipeline/config/publishing.toml`의 모델을 한 곳에서 관리한다. #9에서 잠정 선택한 `opus`를 사용하며 사람 판정 뒤 모델이 확정되면 이 설정을 수정한다. 병합 기본값은 `enabled=false`다. 운영자는 첫 실행의 계정·Git 상태·로그를 직접 확인할 준비가 된 뒤 `true`로 바꾼다. `enabled=false`이면 다음 예약 실행부터 수집·분석까지만 수행한다. `push=false`이면 로컬 카드 생성까지만 수행하며 Git 푸시는 하지 않는다. 실행 시작 때 읽은 설정은 해당 실행에 유지되므로 파일 수정만으로 이미 시작된 작업을 중단하지 않는다. 공개 설정이 잘못되면 네트워크 수집 전에 실패하고 그날의 수집 시도를 소모하지 않는다.

`max_new`는 이번 실행의 새 AI 추출 공지 수(양의 정수)이며 첫 운영 기본값은 5건이다. publisher의 `--max-new`로 전달한다. 기존 30건 대신 5건으로 시작하는 이유는 1시간 예약 제한 안에서 수집과 후속 검증·푸시에 시간을 남기기 위해서다. 남은 공지는 추출 캐시를 유지한 채 다음 날 처리한다.

선택 칸 `cross_model`(예: `"sonnet"`)을 두면 publisher의 `--cross-model`로 넘겨 교차 검증을 켠다(#15, 검증기가 두 모델의 값이 같은 핵심 항목을 자동 검증 통과로 올린다). 허용 모델이고 `model`과 달라야 하며, 아니면 수집 전에 설정 오류로 멈춘다. 없으면 교차 검증을 하지 않는다. 교차 호출은 주 모델 다음에 같은 `max_new`만큼 더 부르므로 시간 예산이 늘어난다. 확인 호출 1회와 새 추출 `max_new`회가 한 번 더 붙는다. 첨부 입력(#112)으로 생긴 재추출이 끝난 뒤 켜는 것을 권한다. 교차 단계가 멈춰도(확인 호출 실패 등) 주 결과로 카드는 공개된다(`extractor/daily.py`의 교차 단계 처리). 주·교차 호출은 하루 호출 상한(`--max-calls`, 기본 60)을 함께 쓰며, 이 실행은 상한을 따로 넘기지 않는다. 상한에 닿으면 교차 쪽이 다음 날로 넘어간다. 일일 로그의 `publish_started`에 `cross_model`이 남는다.

선택 칸 `images = true`를 두면 publisher의 `--images`로 넘겨 **포스터 이미지도 AI에 넣는다**(#14, 없으면 끔).
- **넣는 방식:** 도구는 계속 모두 끈 채로 둔다. 수집기가 내려받은 이미지(`data/assets/`, 수집 기록의 sha256과 같은 파일, PNG·JPEG·GIF·WebP, 한 장 5MB, 공지당 4장)를 파이프라인이 읽어 `claude -p --input-format stream-json`의 표준 입력에 image 블록으로 넣는다(`extractor/images.py`). 모델이 파일을 읽는 도구가 없어서, 공지 속 "파일을 읽어라" 같은 주입이 따를 길이 없다.
- **확인 호출:** 켜면 확인 호출이 1×1 시험 이미지를 같은 방식으로 보낸다. CLI가 그 형식을 받지 않거나 격리가 어긋나면, 공지를 보내기 전에 멈춘다(종료 코드 2).
- **다시 뽑는 대상:** 켜거나 끄면 포스터가 있는 공지만 다시 뽑는다. 이미지가 없는 공지의 결과는 그대로 쓴다.
- **근거:** 이미지에서 읽은 근거는 글자 대조를 할 수 없어 "사람 확인"으로 간다(`verifier/checks.py`).
- **남은 위험:** 결과 공지(수상자 명단)의 이미지는 넣지 않는다. 다만 모집 공지의 이미지에 이름·학번이 찍혀 있으면 가리지 못하고 AI로 간다.
- **비용:** 이미지 한 장은 대략 `(가로/28)×(세로/28)` 토큰이다.
- **켜기 전에:** 운영 PC에서 아래처럼 한 번 직접 돌려, 확인 호출이 통과하는지와 이미지 근거가 붙은 카드를 본다.

```powershell
cd pipeline
.\.venv\Scripts\python.exe -m extractor daily --model opus --images --max-new 3
```

`collector.daily`를 직접 부를 때 `--publish-config`를 생략하면 기존 수집·분석만 수행한다. 예약 스크립트는 중앙 설정 경로를 명시적으로 넘긴다. 개발 브랜치에서 운영 스크립트를 실행하면 기존 main 가드가 중단시킨다.

```powershell
# 저장소 루트에서 설정만 검증한다. AI·학교·Git 푸시를 호출하지 않는다.
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run_daily_collect.ps1 -ValidateOnly
```

## 공개 여부와 종료 코드

- 이번 수집이 완료되고 저장 공지가 있으며 수집0·분석0일 때만 공개한다. 첨부 HTTP404 등 정책상 경고만 있는 경우는 수집0이므로 허용한다.
- 실제 첨부 오류나 출처 수집 오류가 있어 수집1이면 저장분 분석은 기존처럼 수행하지만 공개하지 않고 전체1을 반환한다. 미완료/저장0건/분석 실패도 공개하지 않는다.
- publisher0: 전체0, 정상 공개.
- publisher1: 전체0, 경고가 있는 정상 공개. 일일 상태의 원래 publisher 종료 코드와 `data/publish_logs/<시각>-export.json`의 카드 id·사유를 확인한다. 일일 공개 로그의 `export_report.file`이 해당 보고 파일을 가리킨다.
- publisher2: 전체2, 공개 중단. 기존 cards.json 보존 계약을 따른다.
- publisher3: 전체3, 새 cards.json이 로컬에 있지만 푸시 실패. 성공으로 처리하지 않는다.
- publisher 예외·0~3 밖 반환값: 전체1, `failure_phase=publish`와 예외 종류를 기록한다. Ctrl+C도 상태에 전체1을 남긴 뒤 중단된다.

기록은 `data/daily_status.json`, `data/logs/<날짜>.jsonl`, `data/publish_logs/<날짜>.jsonl`이다. 원문·제목·근거 문장·외부 예외 메시지는 일일 로그에 남기지 않는다. 공개 상태·단계·종료 코드·고정 진단과 건수만 기록한다. 일일 JSONL의 `publish_finished.reason`은 `published`·`published_with_warnings`·`publish_stopped`·`push_failed` 중 하나이며 원본 stderr는 복사하지 않는다. 예외·잘못된 반환값은 `failed` 이벤트의 예외 종류와 `phase=publish`로 구분한다.

## 실패와 재시도

같은 날의 두 번째 일일 실행은 다시 수집하거나 AI를 부르거나 공개하지 않는다. 상태 파일을 지워 이 제한을 우회하지 않는다. 단, 직전 공개가 2·3이면 같은 날 재실행도 같은 실패 코드를 반환하며, 공개 중 예외·Ctrl+C·강제 종료이면 1을 반환한다. 상태 파일과 마지막 공개 결과를 유지해 예약 실행 결과가 성공으로 덮이지 않게 한다. 공개 직전에 진행 상태를 디스크에 저장하므로 강제 종료도 다음 실행이 실패로 감지한다. 공개만 자동 재시도하는 경로는 추가하지 않는다. 일시적 오류 재시도에도 AI 호출·Git 상태를 다시 판단해야 하므로 이번 변경은 리뷰에서 제안한 최소 대안인 실패 코드 유지를 택한다. 공개2·3이나 비정상 종료는 운영자가 로그를 확인한다. 푸시3의 카드/로컬 커밋은 기존 publisher 규칙에 따라 다음 정상 실행에서 정리해 올릴 수 있다. 당일 수동 publisher 재시도는 운영자가 계정·호출 상한·원문/분석 최신성·Git 상태를 확인한 뒤 판단한다.

운영은 전용 main checkout, 본인 Claude 로그인, 비대화형 Git 인증이 필요하다. 환경 API 계정으로 우회하거나 격리 옵션을 제거하지 않는다. 설정에서 공개를 비활성화해도 기존 공개 카드가 자동 삭제되지는 않는다. 사이트의 마지막 갱신 시각과 배포 결과를 확인한다.

강제 종료 후에는 먼저 예약 작업과 관련 Git·Python 프로세스가 끝났는지 확인한다. `.git`이 파일인 worktree에서는 `git rev-parse --git-path index.lock`으로 실제 잠금 위치를 확인한다. `.git/index.lock`(또는 확인한 잠금 위치)과 `site/data/cards.json.*.tmp`가 남았는지 살펴보고, 실행 중인 프로세스가 없다는 확인 후 남은 임시 파일만 정리한다. 잠금이 있다는 이유만으로 실행 중인 Git의 잠금을 지우지 않는다. `git status`·`git log`와 원격 카드도 대조한다.

`push=false`로 확인한 뒤 로컬 카드 변경을 버리려면 생성 결과를 먼저 검토·보관하고 `git checkout -- site/data/cards.json`을 실행한다. 이 명령은 커밋되지 않은 카드 변경을 버린다. `push=false`는 Git 커밋을 만들지 않지만, 이전 푸시 실패로 남은 커밋은 별도로 확인해야 한다.

기존 예약 정의의 `ExecutionTimeLimit`은 1시간이다. 초기 설정의 수집20분 + 확인 호출1회·새 추출5회 × 호출당300초는 호출 제한만 합쳐 약50분이다. 나머지 약10분을 규칙 분석·검증·Git 작업 등에 남긴다. 이는 전체 실행의 엄격한 시간 보장은 아니다. 첨부 처리·CLI 준비 등 부대 시간이 있고 `max_new`나 수집 시간 예산을 늘리면 1시간을 넘길 수 있으므로 첫 운영 소요를 확인한 뒤 조정한다. 이 경로는 교차 모델을 자동 활성화하지 않는다. 이후 교차 모델을 연결하면 추가 호출 예산도 다시 계산해야 한다. 스케줄러가 강제 종료하면 실행은 완료 성공으로 기록되지 않으며 아직 공개 단계에 도달하지 않은 결과를 새로 배포하지 않는다. 저장된 추출 캐시는 다음 정상 실행에서 재사용한다. 다만 종료 시점이 카드 생성/푸시 구간이면 로컬/원격 카드와 publish_logs를 직접 확인해야 한다. 이 변경은 예약 제한을 늘리거나 작업을 재등록하지 않는다. 실제 일일 소요를 관찰해 한도 조정이 필요한지는 운영자가 별도로 결정한다.

## 검증 범위

회귀는 합성 수집 결과와 가짜 publisher로 잠금 보유·호출 순서·부분 실패 차단·종료 코드·같은 날 중복 실행 방지와 공개 실패 코드 유지를 검증한다. 실제 하루 이상 자동 성공과 DB 백업 운영 확인은 #19의 별도 완료 기준이다. 수동 첫 공개 성공 기록은 #63의 2026-11-14 댓글에 있으며 이번 코드 검증과 구분한다.
