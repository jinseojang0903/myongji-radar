# 매일 수집과 카드 공개 연결 (#63)

## 실행 경로

`scripts/run_daily_collect.ps1` → `collector.daily --publish-config config/publishing.toml` → 수집 → 규칙 분석 → publisher(추출·검증·내보내기·카드 한 파일 main 푸시) 순서다. CollectorLock은 전체 구간에 유지한다. publisher 자체는 별도 잠금을 잡지 않으며 일일 실행기가 잠금을 보유한 상태로 호출한다.

기존 예약 작업은 같은 스크립트를 호출하므로 병합 후 최신 main을 운영 PC에 받으면 새 흐름을 사용한다. 이 PR 작업에서 작업 스케줄러를 새로 등록/변경하거나 실제 운영 수집·AI 호출·공개를 실행하지 않는다.

## 중앙 설정

`pipeline/config/publishing.toml`의 모델을 한 곳에서 관리한다. #9에서 잠정 선택한 `opus`를 사용하며 사람 판정 뒤 모델이 확정되면 이 설정을 수정한다. `enabled=false`이면 다음 예약 실행부터 수집·분석까지만 수행한다. `push=false`이면 로컬 카드 생성까지만 수행하며 Git 푸시는 하지 않는다. 실행 시작 때 읽은 설정은 해당 실행에 유지되므로 파일 수정만으로 이미 시작된 작업을 중단하지 않는다. 공개 설정이 잘못되면 네트워크 수집 전에 실패하고 그날의 수집 시도를 소모하지 않는다.

`collector.daily`를 직접 부를 때 `--publish-config`를 생략하면 기존 수집·분석만 수행한다. 예약 스크립트는 중앙 설정 경로를 명시적으로 넘긴다. 개발 브랜치에서 운영 스크립트를 실행하면 기존 main 가드가 중단시킨다.

```powershell
# 저장소 루트에서 설정만 검증한다. AI·학교·Git 푸시를 호출하지 않는다.
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run_daily_collect.ps1 -ValidateOnly
```

## 공개 여부와 종료 코드

- 이번 수집이 완료되고 저장 공지가 있으며 수집0·분석0일 때만 공개한다. 첨부 HTTP404 등 정책상 경고만 있는 경우는 수집0이므로 허용한다.
- 실제 첨부 오류나 출처 수집 오류가 있어 수집1이면 저장분 분석은 기존처럼 수행하지만 공개하지 않고 전체1을 반환한다. 미완료/저장0건/분석 실패도 공개하지 않는다.
- publisher0: 전체0, 정상 공개.
- publisher1: 전체0, 경고가 있는 정상 공개. 일일 상태의 원래 publisher 종료 코드와 publish_logs를 확인한다.
- publisher2: 전체2, 공개 중단. 기존 cards.json 보존 계약을 따른다.
- publisher3: 전체3, 새 cards.json이 로컬에 있지만 푸시 실패. 성공으로 처리하지 않는다.

기록은 `data/daily_status.json`, `data/logs/<날짜>.jsonl`, `data/publish_logs/<날짜>.jsonl`이다. 원문·제목·근거 문장·외부 예외 메시지는 일일 로그에 남기지 않는다. 공개 상태·단계·종료 코드·고정 진단과 건수만 기록한다.

## 실패와 재시도

같은 날의 두 번째 일일 실행은 다시 수집하거나 AI를 부르거나 공개하지 않는다. 상태 파일을 지워 이 제한을 우회하지 않는다. 공개2·3이나 비정상 종료는 운영자가 로그를 확인한다. 푸시3의 카드/로컬 커밋은 기존 publisher 규칙에 따라 다음 정상 실행에서 정리해 올릴 수 있다. 당일 수동 publisher 재시도는 운영자가 계정·호출 상한·원문/분석 최신성·Git 상태를 확인한 뒤 판단한다.

운영은 전용 main checkout, 본인 Claude 로그인, 비대화형 Git 인증이 필요하다. 환경 API 계정으로 우회하거나 격리 옵션을 제거하지 않는다. 설정에서 공개를 비활성화해도 기존 공개 카드가 자동 삭제되지는 않는다. 사이트의 마지막 갱신 시각과 배포 결과를 확인한다.

기존 예약 정의의 `ExecutionTimeLimit`은 1시간이다. 수집20분과 기본 최대30건 추출(호출당 최대300초)은 최악의 경우 이 한도를 넘길 수 있다. 스케줄러가 강제 종료하면 실행은 완료 성공으로 기록되지 않으며 아직 공개 단계에 도달하지 않은 결과를 새로 배포하지 않는다. 저장된 추출 캐시는 다음 정상 실행에서 재사용한다. 다만 종료 시점이 카드 생성/푸시 구간이면 로컬/원격 카드와 publish_logs를 직접 확인해야 한다. 이 변경은 예약 제한을 늘리거나 작업을 재등록하지 않는다. 실제 일일 소요를 관찰해 한도 조정이 필요한지는 운영자가 별도로 결정한다.

## 검증 범위

회귀는 합성 수집 결과와 가짜 publisher로 잠금 보유·호출 순서·부분 실패 차단·종료 코드·같은 날 재시도 방지를 검증한다. 실제 하루 이상 자동 성공과 DB 백업 운영 확인은 #19의 별도 완료 기준이다. 수동 첫 공개 성공 기록은 #63의 2026-11-14 댓글에 있으며 이번 코드 검증과 구분한다.
