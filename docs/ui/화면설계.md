# 화면 설계 (#20)

> 2026-11-03 초안. 목업: `docs/ui/mockups/` (브라우저로 `home.html`을 열면 4화면을 오갈 수 있다).
> 예시 데이터는 2026-10-15 기준 실제 교내 공지 4건이다 (예선 때 프롬프트 v0.1로 추출한 3건 + 원문을 직접 확인한 ABI-X 해커톤). **수집기가 모은 데이터가 아니다.** 판정은 신청 가능·확인 필요·불가 3가지가 보인다. 역사 영상은 "팀 구성 시 가능" 예시였으나 제외 대상이 "원문 확인 필요"라 계약 3절 순서대로 "확인 필요"로 고쳤다 (11/4 리뷰). "팀 구성 시 가능"은 실제 데이터로 보여 준다.
> **검수 상태 배지("검수 완료" 등)와 판정 결과, 문의 초안 문장, 마지막 확인 시각은 화면을 설명하려고 정한 값이다.** 실제 검수·판정 결과가 아니므로 발표 자료에 그대로 쓰지 않는다. 실제 사이트(#21~)의 예시 데이터는 수집기 + AI 추출 결과로 만든다.
> 디자인 AI(미리캔버스·이미지 생성 등)는 쓰지 않았고, Claude Code가 HTML·CSS로 작성했다.

## 1. 원칙

1. **AI를 믿게 하지 않고 확인하게 한다.** 모든 값 옆에 상태(검수 완료·자동 검증·확인 전·원문 확인 필요·정보 없음)와 근거를 둔다.
2. **"정보 없음"은 "제한 없음"이 아니다.** 화면 문구로 매번 밝힌다.
3. **색만으로 구분하지 않는다.** 판정과 상태 배지는 기호(● ◆ ? ✕ ✓ !)와 글자를 함께 쓴다.
4. **휴대폰 우선.** 520px 이하에서 한 열, 항목 표는 라벨 위·값 아래.
5. **인터넷 없이 열린다.** 외부 글꼴·라이브러리를 쓰지 않는다 (행사장 시연 대비).
6. **개인정보를 받지 않는다.** 로그인·학번 없음, 내 조건은 브라우저에만 저장.

## 2. 화면 흐름

```
홈 ──(내 조건으로 찾기)──▶ 맞춤 추천 ──(카드 보기)──▶ 카드 상세
 │                                                      │
 └──────────(카드 클릭)───────────────────────────────────┘
상단 메뉴: 홈 · 맞춤 추천 · 제작 기록 (어느 화면에서나)
```

**결선 3분 시연 동선 (안):** 맞춤 추천에서 문장 입력 → 인식한 조건 칩 확인 → 판정 결과(신청 가능·확인 필요·불가, 실제 데이터에 있으면 팀 구성 시 가능) → 역사 영상 카드 상세(근거 펼침, 마감 변경 이력, 정보 충돌, 문의 초안 복사, 캘린더) → 제작 기록(규칙 vs AI 정확도, AI 검수 체험). [윤민기 검토]

## 4. 상태 표시 규칙

**항목 상태** (`docs/api-contract.md`의 `status`)

| 화면 표시 | 계약 값 | 언제 | 모양 |
|---|---|---|---|
| ✓ 검수 완료 | `human_verified` | 팀이 원문과 대조함 | 초록 |
| 자동 검증 통과 | `auto_verified` | 근거 문장 실재·교차 추출 일치·형식 검사 통과 | 파랑 |
| 확인 전 | (`auto_verified`·`ai`인 핵심 항목) | 신청기간·자격이 아직 사람 대조 전 | 회색 점선 테두리 |
| ! 원문 확인 필요 | `needs_check` | 검증 실패, 정보 충돌, 해석이 애매함 | 주황, 이유 한 줄 필수 |
| 정보 없음 | `missing` | 공지에 없음 | 회색 기울임 "공지에 없음" |

**판정** (`site/js/rules.js` 결과)

| 화면 표시 | 계약 값 | 함께 보여 줄 것 |
|---|---|---|
| ● 신청 가능 | `eligible` | 맞은 조건 요약 (✓) |
| ◆ 팀 구성 시 가능 | `team_needed` | 필요한 팀 인원 |
| ? 확인 필요 | `check` | 무엇이 없거나 확인 전인지 + 문의 초안 버튼 |
| ✕ 불가 | `ineligible` | 맞지 않는 조건과 근거 문장. 근거가 확인 전이면 "확인 전 정보" 표시 |

**카드 단위 배지** (목록·추천 화면)

- "✓ 검수 완료"는 핵심 항목(`apply`, `campus`, `grades`, `enrollment`, `team`)이 **모두** `human_verified`일 때만 붙인다.
- 핵심 항목 중 하나라도 `needs_check`면 "! 원문 확인 필요", 그 밖에 사람 대조 전이면 "확인 전"을 붙인다. 무엇이 확인 전인지 알 수 있게 "신청기간 확인 전"·"자격 확인 전"으로 나누고, 핵심 항목이 공지에 없으면 "공지에 없는 조건 있음"을 따로 붙인다 (#21). 계약에는 항목 단위 `status`만 있으므로 화면(#21)이 이 규칙으로 계산한다.

**기타**

- **마감 변경:** 목록에서는 주황 줄 "⚠ 마감 변경: 이전 → 새 값", 상세에서는 이전 값 취소선 + 출처 공지 + 확인 일시.
- **정보 충돌:** 값을 하나로 고르지 않고 출처별 값을 모두 보여 준다. 마감처럼 우선 값이 필요하면 최신 공지 값을 쓰고 그 사실을 밝힌다. 계약에 충돌 표시가 따로 없어, 카드 상세(#25)는 `needs_check`이면서 **근거 문장이 서로 다를 때**만 충돌로 표시한다 (같은 문장이 본문·이미지에 함께 나온 것은 충돌이 아님).
- **시각 미기재:** "시각 미기재"로 쓰고, 캘린더에는 하루 종일 일정으로 넣는다. 23:59 등으로 채우지 않는다.
- **캘린더 알림:** 3일 전·1일 전. 시각이 있으면 마감 시각 기준, 하루 종일 일정은 그 날 0시 기준이라 자정에 울리지 않게 오전 9시로 맞춘다. 마감이 아닌 단계(예선·본선·발표·시상)는 제목에 "[마감]" 대신 "[일정]"을 붙인다 (예선은 제출 마감인지 심사일인지 공지마다 달라 마감으로 단정하지 않음).
- **이미지에서 읽은 근거:** 위치 태그 `이미지` + "이미지에서 읽음" (본문·PDF 근거보다 신뢰도가 낮음).
- **D-day:** 7일 이내는 빨강, 그 밖은 회색. 마감이 지난 대회는 목록에서 뺀다 (제작 기록·검색용 보관은 별도).

## 5. 데이터 계약 보완

- **반영됨 (PR #30):** 대상 문장이 "정규학기 학부 재학생"처럼 학년·캠퍼스를 구분하지 않으면 `"any"`, 근거는 그 대상 문장. 대상 문장 자체가 없으면 `missing`. 개인 참가 가능 여부가 없으면(`team.individual_ok: null`) 개인 참가 학생은 `check`.
- **#22에서 계약 3절에 반영:**
  1. **불가 판정과 확인 전:** 근거가 있는 자격 불일치는 확인 전이어도 `ineligible`로 내되, 화면에 "확인 전 정보" 표시를 붙인다 (계약 3절 판정 순서 1번 유지).
- **#17에서 결정:** 목록 한 줄 요약과 출처 게시판 이름을 카드에 넣을지. 지금은 화면에서 fields로 조합한다.
